STRONG

A-1 · Make parser quality explicit

The Go parser deliberately preserves source-only analysis after parse failure. That gives text detectors value, but parse quality is absent from the parser interface and invisible to engine/output policy.

Before

ParseSource → unit; parse error is locally discarded. AST omissions cannot cross the seam.

→

After

Parse result → unit + explicit quality/diagnostic. Engine owns continue, text-only, warn, or fail policy.

Leverage: one parser-quality interface feeds every language and output policy. Locality: parser-policy knowledge stops leaking into plugins and CLI. Deletion test: deleting it spreads the decision again, so it earns its module.

internal/lang/go/plugin.go:61–71 · internal/engine/analyzer.go
WORTH EXPLORING

A-2 · Narrow detector capabilities

The detector interface currently carries lifecycle, cache-state, finalization, reset, metadata, and run behaviour. Stateless detectors cross a broad interface and inherit no-op methods.

Before

Every detector learns one wide interface, even when it only runs rules.

→

After

A narrow detector module plus optional lifecycle/cache/finalization capabilities at the engine seam.

Condition: first add catalogue/factory parity validation. One concrete language adapter means this should not become a premature abstraction.

internal/core/detector.go · internal/engine/registry.go · internal/engine/analyzer.go
WORTH EXPLORING

A-3 · Make multi-root cache identity order-invariant

The first requested root defines cache-relative keys; later roots can use ../ keys. This is safe but order-dependent, and first-root policy exists in both scope resolution and analyzer setup.

Before

[root A, root B] → B is keyed relative to A. Reordering changes persisted identities.

→

After

One ScanScope-owned canonical key space accepts each root and is passed directly to the analyzer.

Acceptance: prove order invariance, mixed file/directory roots, and persisted-cache reuse before changing the seam.

internal/engine/scan_scope.go:19–50 · internal/engine/analyzer.go:185–190
WORTH EXPLORING

A-4 · Stage CLI execution only on real variation

Plan resolution and scope have been extracted, but run still manages cache, baseline, analyzer construction, reporting, export, and exit policy. It is a real pending checklist item, not a reason for a framework rewrite.

Before

One CLI function coordinates execution and every output/exit decision.

→

After

Private scan-execution and output/exit-policy modules behind the same single Run interface.

Condition: wait until a second output or exit-policy variation is real; one adapter remains hypothetical today.

It gives the engine and users an honest, testable result while retaining the intentional source-only fallback. The other candidates are conditional and should wait for a second language, repeat multi-root cache friction, or a second output policy.
